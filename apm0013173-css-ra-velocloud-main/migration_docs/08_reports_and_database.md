# Reports and database behavior

Report calculations/builders remain unchanged in `api/docs_mds.py`, `api/docs_other.py`, `api/doc_utils_helpers.py`, and the view methods. Original runtime `calls`, documents and templates remain available at the same module-relative paths. This migration does not fix calculation defects or alter workbook names, labels or business rules.

Evidence includes the original report regression tests plus `test_hwstats_real_business_and_workbook` (real JSON/XLSX encoding and workbook values/styles, identical SQL/parameters and cursor/connection cleanup) and `test_mds_report_http_workbook_parity` (the distinct `/api/report/mds`, real eight-sheet workbook with empty inventory, values/styles/merged ranges, response metadata, exact six upstream calls). Existing tests also cover capacity/date boundaries, chart/workbook structure, policy ordering, event downtime and bounded numeric parsing. Workbook bytes are not required to match ZIP creation timestamps; decoded semantic content is compared.

Limit: empty-inventory MDS success does not verify populated profile/segment/policy sheets. Most report paths are unexecuted, as reflected in coverage. No assertion of all report or numerical parity is warranted. `/api/mds/` retains its real four-versus-six argument defect (document 04).

MySQL remains the original connector and SQL; no ORM or SQL rewrite was introduced. Hardware statistics integration uses environment names `VELO_DB_HOST`, `VELO_DB_USER`, `VELO_DB_PASS`. Tests replace only the connection/cursor; live server versions, permissions, timezones, customer tables, data types and large result sets must be validated in dev/test.

SQLite authentication/session storage uses stdlib `sqlite3`. `auth_schema.sql` is the original empty Django migration schema/default metadata captured from the baseline, including indexes/constraints and migration history; it contains no production users, tokens or credentials. Native `migrate --noinput` bootstraps only a completely empty database. Existing nonempty databases require the three active authentication tables and are not rebuilt or upgraded. Missing required tables cause an explicit failure rather than guessing a schema migration. The differential bootstrap test compares original schema and confirms an existing database remains unchanged.

The original private temporary SQLite location, ownership checks and pod-local lifetime are preserved. This does not add persistence across replicas or pod replacement. Retain original record data and the signing secret; have an operator back up and restore any actual database before changing deployments. No application schema/data migration or production copy was performed. Historical management commands for future Django schema upgrades are outside this fixed-schema native bootstrap and require a separately reviewed upgrade plan if needed.
